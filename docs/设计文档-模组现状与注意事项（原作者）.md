## 1. 现在有什么

### 1.1 游戏内注册内容

总共 4 个注册对象，全部由 `com.trialportal.registry` 下的 `DeferredRegister` 注册：

| 类型 | ID | 说明 |
|---|---|---|
| 方块 | `trial_portal:challenge_portal` | 闯关传送门，`TrialMode.CHALLENGE` |
| 方块 | `trial_portal:tower_portal` | 爬塔传送门，`TrialMode.TOWER` |
| 方块 | `trial_portal:trial_portal` | 试炼传送门，`TrialMode.TRIAL` |
| 物品 | 上面三个的 `BlockItem` | 只用于放置，无特殊行为 |
| 方块实体 | `trial_portal:trial_portal` | 三个方块共用同一个类型，只存「绑定到哪份试炼」 |
| 创造栏 | `trial_portal:main` | 「试炼传送门」标签页，装三个方块 |

三个方块共用 `TrialPortalBlock` 一个类，差别只有构造时传入的 `TrialMode`；方块实体也只有一个类型（`BlockEntityType.Builder.of` 支持多个方块共用）。

两条设计主线值得先记住，改动时不要破坏：

1. **模式差异只收敛在极少数几处**：`TrialMode` 声明差异（`isEndless()` / `isPlayerDriven()`），`TrialManager.onWaveCleared()` 和 `onPlayerDeath()` 是唯一按模式分支的地方。新增第四种玩法时照着这两处加分支即可，不需要动生成/判定/发奖。
2. **内容与逻辑分离**：出什么怪、给什么奖励、BOSS 克制什么全部走数据包 JSON；Java 侧只提供「怎么跑」。所以调平衡不该改代码。

### 1.3 数据包内容

`src/main/resources/data/trial_portal/` 下自带：

- `trials/`：`challenge.json`（5 波）、`tower.json`（无尽，4 个层段覆盖到 9999 层，每 10 层一个 BOSS，每 5 层发奖）、`trial.json`（1 波前置小怪 + 1 只带 3 条词条的 BOSS）
- `boss_affixes/`：8 条词条（破甲 / 碾碎 / 追猎 / 荆棘 / 耐火 / 禁空 / 疾走 / 坚壁），具体克制逻辑见配置指南 §5
- `loot_tables/blocks/`：三个方块掉自己
- 另外 27 个资源文件里包含 `assets/`（方块状态、模型、中英文语言）和 `META-INF/mods.toml`

### 1.4 配置与指令

- **配置**：`config/trial_portal-common.toml`，16 项，分 4 组（challenge 2 / tower 4 / trial 3 / general 7）。所有读取都发生在使用时（`TrialConfig.XXX.get()`），所以改完保存后新开的会话就用新值；没生效就重启一次。
- **指令**：`/tei trial` 下 8 条子命令（list / start / stop / status / bind / floor / profile / affixes），权限等级 2。

### 1.5 明确还没有的东西

这些不是 bug，是当前边界，做需求前先确认：

- **没有配方**。三个传送门方块既没有 `recipes/*.json`，也没有获取途径说明，只能靠创造物品栏或手动 `/give trial_portal:challenge_portal` 之类的指令获得。要进正常生存流程，必须补配方 JSON（`data/trial_portal/recipes/`）。
- **没有客户端代码**。全部是服务端逻辑，没有 GUI、按键绑定、`client` 侧类，也没有 Jade / WTHIT 这类方块信息集成。所以方块实体绑定了哪份试炼，玩家在游戏里看不出来（只能靠 `/tei trial bind` 的记忆）。
- **没有游戏内测试**。`src/test` 不存在，`runGameTestServer` 里没有注册任何 GameTest；`checkTrialData` 是唯一自动化校验，且它只覆盖数据包解析。
- **不是真正的传送门**。方块是实心方块，作用相当于「试炼入口交互终端」，走不进去也不传送。
- **没有组队**。会话是「一人一场」，见 §4.4。
- **没有进度 / 成就 / 统计**，也没有跨存档的排行榜（爬塔记录存在世界存档里）。

## 2. 一次右键的完整链路

调代码时按这条链找位置：

```
玩家右键传送门
  └─ TrialPortal.onRightClickBlock    （仅「潜行 + 手持物品」时需要，强制放行方块使用）
      └─ TrialPortalBlock.use
          ├─ TrialLibrary.resolve(mode, 方块实体绑定的ID)   → 得到 TrialDefinition
          │     （绑定为空时取该模式下 ID 字典序最靠前的一份）
          └─ TrialManager.hasSession ?
              ├─ 否 + 潜行 → 提示「潜行是结算，开始请直接右键」
              ├─ 否 + 空手 → TrialManager.start(player, def, pos)   ← pos 就是生成中心
              │                  └─ beginWave() → spawnOne() ×N
              │                        └─ 按需：applyNbt → scaleForFloor → applyBossAffixes
              └─ 是       → TrialManager.onPortalUse(player, sneaking)
                             ├─ AWAITING_DECISION + 潜行 → end(SETTLED) 发奖
                             ├─ AWAITING_DECISION + 空手 → 转入 INTERMISSION 倒计时
                             ├─ INTERMISSION      + 潜行 → end(SETTLED) 发奖
                             ├─ INTERMISSION      + 空手 → 提示「即将开始」
                             └─ IN_WAVE                  → 提示「本波还没打完」
```

推进由 tick 驱动（`TrialEvents.onServerTick` → `TrialManager.tick`，默认每 10 tick 判一次）：

```
每次判定，对每个会话依次做：
  1. 玩家在线吗？        → 不在：清怪 + 丢掉会话（发奖流程不走，见 §4.4）
  2. 定义还在吗？        → 不在（数据包被改）：中止
  3. 原点区块加载了吗？  → 没加载：跳过本轮（不判定、不倒计时）
  4. 玩家在范围内吗？    → 不在：中止，累计奖励作废
  5. 清理已死亡的怪（aliveMobs 里查不到实体或已死）
  6. 按状态：
       IN_WAVE            → aliveMobs 空 = 通过 → onWaveCleared()
       INTERMISSION       → timer -= 间隔；到点 → advance()
       AWAITING_DECISION  → 什么都不做（等右键）
```

状态机（三种模式的差异就在走不走 `AWAITING_DECISION`）：

```
闯关 CHALLENGE:  IN_WAVE → AWAITING_DECISION →(右键)→ INTERMISSION → IN_WAVE …
爬塔 TOWER:      IN_WAVE → INTERMISSION → IN_WAVE …            （自动接波，不等玩家）
试炼 TRIAL:      同闯关，最后一波是 BOSS，打完直接结算
```

## 4. 要注意的点

### 4.1 实现与文档不一致的四处（真问题，建议择机修）

**① `tiers[].boss_affix_pool` 写了不生效。**

`Tier` 有这个字段（`TrialDefinition.java:253`），`checkTrialData` 也会校验它引用的词条是否存在，但运行时 `TrialManager.applyBossAffixes()` 只读 `scaling.boss_affix_pool`：

```java
// TrialManager.java:348 —— 注意这里没有看 tier.boss_affix_pool
} else if (definition.scaling != null && definition.scaling.boss_affix_pool != null) {
    pool = definition.scaling.boss_affix_pool;
}
```

配置指南把 `tiers[].boss_affix_pool` 描述为「该层段专用词条池」，实际不生效。当前 `tower.json` 只用了 `scaling.boss_affix_pool`，所以看起来正常。要支持分层的词条池，得在 `spawnOne` 里把命中的 `Tier` 传下来（或让它先回填到一个临时变量上）。

**② 「BOSS 层取 `mobs[0]`」只在 `boss_affix_pool` 非空时成立。**

`ScalingRule.build()` 的实际逻辑是：

```java
// TrialDefinition.java:330
boolean bossFloor = boss_every_floors > 0 && floor % boss_every_floors == 0;
String mob = tier.mobs.get(floor % tier.mobs.size());        // 默认按层数轮换
if (bossFloor && boss_affix_pool != null) {                  // ← 额外条件
    mob = tier.mobs.get(0);                                  // 才是「取第一个」
}
```

也就是说：如果你**不配** `boss_affix_pool` 而只配了 `boss_every_floors`，BOSS 层会按轮换随机取怪，而不是取 `mobs[0]`。配置指南里那条「想让 30 层以上刷掠夺者当 BOSS，就把 `minecraft:ravager` 写在 `mobs[0]`」的约定要补一句前提。

**③ 生成上限是「丢弃」不是「推迟」。**

`TrialConfig.java:116` 的注释说「达到上限时本波剩余的怪会推迟生成」，但 `TrialManager.java:240-256` 的实现是 `budget = min(max_spawns_per_wave, max_alive_mobs)`，超出的部分直接 `break` 掉（只打一条 warn 日志），**不会在下一波补**。上限本身默认 64 / 80，正常配置碰不到，但基于「会补」来做玩法设计会踩空。

**④ `multiply_total` 用瞬态修饰符实现，区块重载后会丢。**

`BossAffixLibrary.java:221` 用 `instance.addTransientModifier(...)` 实现 `multiply_total`。已核对 1.20.1 源码：`AttributeInstance.save()` 只写 `permanentModifiers`，而 `LivingEntity` 的属性是随实体存档的（`"Attributes"` 标签）。因此：

- `add` / `multiply_base` / `set` 改的是 `baseValue` → **会存档**，区块卸载重载、重启服务器都还在。
- `multiply_total` 是瞬态修饰符 → **不进存档**。区块一卸载再加载，BOSS 的这项加成会消失（同一只 BOSS，玩家走远再回来就变弱了）。

更麻烦的是词条只在 `spawnOne()` 里应用一次，实体从 NBT 恢复时不会重跑。当前 8 条示例词条用的是 `add` / `multiply_base` / `set`，没有一条用 `multiply_total`，所以还没暴露。要修的话有两个方向：改用 `addPermanentModifier`（会存档，但同名/同 UUID 需要注意），或者在实体加载时重跑一次词条。

对照一下：**免疫和近战伤害类型走的是 `getPersistentData()`**（Forge 的 `ForgeData` 标签，会随实体存档），所以这两项在区块重载后是安全的。

### 4.2 配置与数据包

- **未知字段静默忽略**。Gson 用 `setLenient()` 反序列化，字段名拼错（`display_nam`、`reward_every_floor`）**不会报任何错**，只是那项配置悄悄不生效。`checkTrialData` 也查不出来。改完 JSON 如果行为不对，第一件事是核对字段拼写。想写备注字段（如 `comment`）也可以放心写，会被忽略。
- **数据包里的数字不做范围校验**。`spawn_radius`、`count`、`weight` 写了负数或超大值，只有 `count <= 0`、空 `mobs`、`from > to`、空 `tiers` 这几项会被 `resolve()` 拦下来，其余全靠 `checkTrialData` 和游戏内表现暴露。
- **`/reload` 会让「引用了被删定义的会话」直接中止**。改完数据包重载，进行中的会话会因 `TrialLibrary.get()` 返回 null 而被判中止（奖励作废）。
- **`checkTrialData` 只校验模组自带的 `src/main/resources/data`**（参数写死在 `build.gradle:131`）。你放在整合包或世界数据包里的 JSON **不在校验范围内**，那边的错误只能靠 `/reload` 后的日志。
- **默认试炼是按 ID 字典序挑的，别的命名空间可能抢走默认**。`TrialLibrary.byMode()` 按完整 ID 字符串排序后取第一个（`TrialLibrary.java:106`）。所以在别的命名空间加一份 `aaa:challenge`，它会排在 `trial_portal:challenge` 前面，成为所有未绑定传送门的默认内容。多个数据包共存时要留意，必要时逐个 `/tei trial bind`。
- **`mode` 与 `endless` 是两个口子**。`endless` 可以手写覆盖（`"endless": true` 会让一份 challenge 定义变成无尽，波次改走 `scaling`）。注意 `scaling` 为空时无尽模式取不到波次 → 直接按通关结算。

### 4.3 指令

- **必须写全命名空间**。指令参数用的是原版 `ResourceLocationArgument.id()`（`TrialCommand.java:70`），它走 `ResourceLocation.read`，缺命名空间时**默认补 `minecraft:`**。所以 `/tei trial start challenge` 会去找 `minecraft:challenge` 然后报「找不到试炼」，正确写法是 `/tei trial start trial_portal:challenge`（tab 补全会给你完整 ID）。
- **`/tei trial start` 的生成中心是玩家脚下**，不是传送门。所以用指令开局时，`abandon_distance` 的判定中心跟着你走，很容易以为「范围检查坏了」。
- **`/tei trial stop` 是管理员语义：不发奖励**，走的是 `Outcome.ABANDONED`。要拿奖励得在游戏里潜行右键结算。
- **`/tei trial bind` 需要看着方块 8 格以内**（`player.pick(8.0, ...)`），且目标方块必须有 `TrialPortalBlockEntity`。

### 4.4 运行时行为

- **会话绑在玩家身上，不在传送门上**。会话只记 `origin` 坐标和试炼 ID，不记传送门。后果有三个：
  1. 一个玩家同时只有一场试炼（`start()` 直接拒绝第二场），做不了组队。
  2. 你可以用**任意一个**传送门（哪怕是另一种模式的）继续/结算当前会话——`onPortalUse()` 完全不看去的是哪个方块。
  3. **拆掉传送门不会中止会话**，会话照常跑，直到你死亡、离开范围或潜行右键。
- **换维度 = 放弃**。`isInsideArena()` 先比维度（`TrialManager.java:633`），维度不同一律判失败。所以打着试炼走进下界/末地传送门，等于放弃。
- **停在 `AWAITING_DECISION` 时走远也会作废奖励**。范围检查在每次判定里无条件执行，先于状态分支。这个玩法没有「暂停」概念，打完一波挂机、跑远一点收个东西，累计奖励就没了。
- **掉线 = 会话结束，累计奖励静默作废**。玩家下线时 `tick()` 只做「清怪 + 移除会话」（`TrialManager.java:545`），不走 `end()`，所以既不发奖也没有任何提示。爬塔层数是在通过每层时逐层写进记录的，所以掉线不会丢层数。
- **打完一波立刻右键不会立刻开下一波**。`AWAITING_DECISION` 状态下右键只是「决定继续」，会把状态转成 `INTERMISSION`，间隔照常从头计（`TrialManager.java:203-214`）。间隔从**玩家按键那一刻**才开始算，所以打完先思考再按键不吃亏。想立即开下一波，把那波的 `intermission_ticks` 配成 `0`。
- **爬塔只能在「层间倒计时」里结算**。`IN_WAVE` 状态潜行右键只得到「本层还没打完」。而爬塔没有 `AWAITING_DECISION` 停留，所以唯一的结算窗口是倒计时那几秒——这一点配置指南没写清，玩家容易以为爬塔无法带奖励离场。
- **原点区块卸载 = 整个会话冻结**。判定第一件事就是 `level.isLoaded(origin)`，没加载就跳过（防止把「没加载」误判成「已清完」）。副作用是：如果玩家跑得很远导致原点区块卸载，会话会一直挂着；等他回到原点区块，第一次判定就会因为「已超出 `abandon_distance`」而中止。另外怪物所在区块卸载会被 `pruneDeadMobs()` 当成「已消失」，本波直接算通过——`abandon_distance` 挡不住这种情况，只能靠别把怪拉太远。
- **只有 `Enemy` 会被设成锁定玩家**（`TrialManager.java:299-304`）。生成牛、村民这类中性/被动生物时它们不会主动攻击，这是设计而非遗漏。
- **所有生成的怪都是 `setPersistenceRequired()`**，不会自然消失。所以忘记清怪会一直留在世界上（`general.clear_mobs_on_end = true` 时结束会清掉）。
- **两个玩家在同一传送门各自打卡不会互相帮忙**：各自刷自己的一份怪，怪只锁定自己的主人。
- **免疫是硬取消**（`LivingAttackEvent` cancel），被打时连击退、音效、受伤动画都没有；也不阻止已经施加的效果（比如已经着火）。
- **近战伤害类型替换会重走一遍受伤流程**。`BossAffixRuntime.onLivingHurt()` 是 `target.hurt(替换后的伤害源, 原伤害)`，因此换成 `minecraft:magic` 之后，其它模组的「魔法抗性 / 魔法免疫」会跟着生效，减伤也会重算一次。事件里的递归保护是 `if (source.is(key)) return;`（`BossAffixRuntime.java:83`），改动这段时不要删掉它。
- **潜行右键为什么要特殊处理**：原版在「潜行 + 手持非空物品」右键方块时会跳过 `BlockState#use()`。传送门恰恰以潜行右键为结算操作，所以 `TrialPortal.onRightClickBlock` 对实现了 `SneakInteractBlock` 的方块强制 `ALLOW`。新增以潜行右键为交互的方块时，记得实现这个接口——否则**空手潜行右键正常、手持物品潜行右键失灵**，是很难查的坑。
- **生成位置是「扫」出来的**，不是精确放置：16 次随机水平取点，每次从初始高度上下各扫 5 格，找「脚下有碰撞、头上两格空」的位置（`TrialManager.java:676`）。扫不到就退回传送门正上方一格，可能卡在方块里。封闭小房间、水下、虚空边打塔都会出问题。

### 4.5 构建与环境

这几条 README 已经写了，属于最容易卡住新环境的三条，这里再点一次：

- **`gradle.properties` 里的 JDK 路径写死了** `<原作者 JDK17 目录>`。换机器/换 JDK 位置必须同步改，否则 Gradle 会尝试从 GitHub 自动下载工具链（国内通常失败）。
- **项目路径含中文**。编译打包不受影响，但如果以后加 `src/test/java` 单元测试，Gradle 的 Test worker 会因非 ASCII 路径加载不了测试类。所以本项目用 `JavaExec`（`checkTrialData`）而不是 `Test` 任务——加新校验工具时照这个模式走，不要引入 `Test`。
- **产物要用 `build/libs/` 里的**（`reobfJar` 重混淆后的），不要用 `build/devlibs/`。
