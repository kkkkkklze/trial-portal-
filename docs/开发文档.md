**这一轮真机抓出的两个真 bug（无头层当时全绿）**：

1. **开局即被判「离开范围」**：越界判定只看「已建房间矩形」，而玩家站在出发平台上（房建在 11 格之外），
   于是开局 5 秒宽限一到就 `本场作废`，人被打回野外。修法是把判定改成**平台半径圈 ∪ 已建区域**，
   并补 4 条纯函数断言（`withinAllowedArea`）。顺带修掉另一半：区域分支**没查维度**，
   在野外同一坐标也会被算「在场」。
2. **离场漏拆最远那间房**：`releaseCell` 的进深原先由调用点各自传，结算/死亡/掉线三条路里只有死亡那条传了，
   真机表现为通关后 `boss_arena` 整间留在虚空里、外加 3 列区块一直被 force。修法是把进深记进 `TrialManager`
   的 `SavedData`（`arena_reach`），拆场时按玩家 UUID 取——**没有可漏传的参数**，而且重启后也还在。
   配套的第三条：建台 force 与拆台 unforce 必须同一套算法（原来一个按「±1 区块」、一个按「±12 格」，
   差在区块边界上，真机留下 `[11,*]` 三个永远还不掉的区块），现由 `cellHalfFootprint()` 统一，
   断言改成「拆完之后场地里不得比开局前多出任何 force 区块」。

## 4e 怪物种类 / 数量 / 强度怎么配（JSON 字段表，2026-09-28）

加一只新怪 = 在 JSON 里写它的实体 ID，**零 Java**；调强弱 = 写 `strength`。三个模式共用同一份字段名。

| 想配什么 | 写在哪 | 字段 |
| --- | --- | --- |
| 种类 | `trials/*.json` 的 `waves[].mobs[].entity`；`scaling.tiers[].mobs`；`challenges/*.json` 的 `difficulties[].mobs[].entity` | 任意已注册实体 ID（含别的 mod 的） |
| 单组数量 | 同上 `mobs[].count` | 整数 |
| **恶意等级** | 同上 `mobs[].malice_level`（守塔/试炼/爬塔的层段/副本档位都能写） | 只在装了 `l2hostility` 时生效。不写＝跟着 `malice` 那套阶梯走；写 `0`＝明说这一档不带恶意；负数与超过 `MaliceLink.LEVEL_CEILING` 在离线门红（§4h） |
| 场上限 / 每波生成上限 | 定义级 `max_alive_mobs` / `max_spawns_per_wave`（0 = 用 `general` 默认）；副本另有 `mob_cap` / `spawn_batch` | 整数 |
| 节奏 | `waves[].intermission_ticks`、`scaling.intermission_ticks`、副本 `spawn_interval_ticks` | tick |
| **强度** | 三层都能写：定义级 `strength`、波次级 `waves[].strength`、层段级 `scaling.tiers[].strength`、终局 BOSS `boss.strength`、副本档位 `difficulties[].strength`、单只怪 `mobs[].strength` | 见下 |
| **外观变体（同一间房换材质）** | `arena_rooms/*.json` 的 `variants[]`：每套可覆盖 `floor` / `wall` / `ceiling_block` / `pillar_block` / `light_block` / `floor_pattern` / `pattern_block`，留空的字段沿用房间默认 | 开局按**会话种子**挑一套，同一场稳定、换一场可能不一样 |
| 地板花纹 | `floor_pattern` = `none` / `checker`（隔格拼花）/ `border`（内圈一道边），第二材质用 `pattern_block`（空 = 用柱子材质） | 名字写错直接红 |
| **落点变体（同一间房换位置）** | `arena_rooms/*.json` 的 `layouts[]`：`{ "name": …, "gap": 与上一间之间的虚空宽度, "lateral": 沿 X 横移 }` | 同样按会话种子挑一套，但取的是种子的**另一段比特**（与外观解耦）。第一间房永远直行——大厅那侧的围栏缺口是按中轴线留的 |
| **房内隔断（把空盒子切开）** | `partitions[]`：`{ "name": …, "from": [dx,dz], "to": [dx,dz], "block": …, "height": 1~室内高 }`，坐标是室内局部格 | 只能轴对齐、不许越出室内、不许压住站怪点或 BOSS 中心舞台（都在离线门红）。房里有隔断封出的不通小间由无头判据拦（见 §10 ㉕） |
| 落点 | 定义级 `spawn_radius` / `spawn_height`；副本档位同名（以前是 Java 常量） | 格 |
| **逐层指定（爬塔）** | `scaling.floors[]`：`{ "floor": 3, "title": "…", "mobs": [ { "entity": …, "count": …, "boss": true, "strength": … } ], "boss": true, "boss_affix_pool": […], "rewards": […], "strength": … }` | 写了的层原样出；没写的层继续走 `tiers` 轮换 |

`strength` 的五个字段：`health_multiplier` / `damage_multiplier` / `speed_multiplier`（倍率，1.0=不变）、
`armor_bonus` / `knockback_resistance`（加值）。**合成规则**：沿"定义 → 波次/档位/层段 → 单只怪"逐层
**乘数相乘、加值相加**；爬塔的 `health_multiplier_per_floor` / `damage_multiplier_per_floor` 折进同一条链，
老 JSON 不用改。
**应用方式**：一律走 permanent 属性修饰符（`MULTIPLY_TOTAL` / `ADDITION`），**不改基值**——
以前 `scaleForFloor` 用 `setBaseValue(base*m)`，于是 SNBT 里写的属性和倍率谁先谁后决定结果；
现在两者互不干扰，且每条属性一个固定 UUID，重复应用不叠层（去掉幂等守卫会直接抛
`Modifier is already applied`，断言已盯着）。实体没有某条属性（例如骷髅没有 `ATTACK_DAMAGE`）时该字段自动跳过。

校验：倍率非负、上限 100（速度 10）、`armor_bonus` 0~100、`knockback_resistance` 0~1——
阈值是为了拦"把 1.5 写成 150"这类百分比误写，`checkTrialData` 与运行期加载都会红。
另外 `mobs[].nbt` 现在会先过一遍 SNBT 解析（以前写错只有运行期一条 warn，等于装备/名字静默没生效）。

## 4f 整合包专用内容与"新建存档开箱就有"（2026-10-12）

datapack 装在 `saves/<世界>/datapacks/` 里**只对那一个存档生效**，新建存档就是白纸。
jar 自带的 `data/` 是全局的，所以要让新档开箱就有内容，内容必须在 jar 里。

| 机制 | 生效范围 | 什么时候用 |
| --- | --- | --- |
| `src/main/resources/data/trial_portal/**` | 所有世界、所有整合包 | 只放**通用**内容（原版实体 ID）。放了某个整合包才有的 ID，换包就是"加载得到、刷不出来" |
| `packOverlays/<name>/data/trial_portal/**`（gitignore，本机） | 只在 `-PpackOverlay=<name>` 构建出来的那份 jar 里 | 整合包专用内容（血量表、逐层爬塔）。公开那份 jar 保持干净 |
| `saves/<世界>/datapacks/<包>` | 只有那一个世界，**优先级高于 jar** | 临时试验。长期用请转成叠加层，否则它会盖住 jar 里的新版本 |

生成 + 构建 + 换进实例：

```bash
python tools/census_to_pack.py --census "<实例目录>/mob-census.tsv" --out build/xb-ladder \
    --id-prefix xb --label "星罗棋布" --floors 100 --emit-table build/xb-ladder/爬塔100层 --overlay xb
./gradlew build -PpackOverlay=xb --offline        # 产出整合包专用 jar（内含 100 层爬塔 + 6 阶副本）
./gradlew build --offline                         # 产出通用 jar（公开分发的那份）
```

两处顺序坑（都是实测，不是猜的）：`processResources` 是"先声明的赢"，所以叠加层要排在
`src/main/resources` **前面**并配 `DuplicatesStrategy.EXCLUDE`；而 `stageOverlayData` 那份 Copy 实测是
"后声明的覆盖先声明的"，于是那边叠加层放后面 + `INCLUDE`。两边规则不一样，所以合并树里到底用了哪份
`tower.json` 由任务自己打出来（`trials/tower.json 来自: 叠加层 / 工程自带（叠加层没生效！）`）——
第一版这里静默拿了工程自带那份去校验，副本数对得上、真正要交付的叠加内容一眼没查过。

`tools/census_to_pack.py --floors 100` 的口径：血量、护甲、攻击力全部取自普查表实测值，不写死任何怪名；
每层一段 `tiers`，本层 `strength.health_multiplier = 该层目标血量 ÷ 该层池子血量中位数`，
全局 `health_multiplier_per_floor` 因此**清零**（两处都开就是把同一份倍率乘两遍）。
为什么不用全局逐层倍率：原版 `generic.max_health` 是 `RangedAttribute(20, 1, 1024)` 且会夹基值，
默认 0.18 的逐层倍率滚到 100 层是 ×18.8，顶层全部撞到 1024 被夹平——"第 90 层"和"第 100 层"其实一样硬。
所以曲线封顶在 1000（`CEILING`），顶上去不动了就换轴：只数、护甲、击退抗性、伤害、BOSS 词条照旧上升。

生成器自己带两把尺（不过就不出包）：`verify_floors` 管逐层（层号连续、ID 都在普查里、有效血量严格上升且不超 1024、
BOSS 层每 10 层一个），`verify_ladder` 管副本三档（拿**夹平后**的实际血量算中位数，血量到顶时必须别的轴在涨）。
后者是本轮被逼出来的：顶阶 `hard` 原先写 ×1.8 配 1000 血的怪，JSON 里看着比 `easy` 难，游戏里两个数都是 1024。

**怪池还要过一道"这是不是一只打得过的怪"的形状判据（2026-10-12 ㊹）**。整合包会把伤害特效注册成实体，而它们照样有 `attack_damage` 与血量（照抄宿主），所以"血量高"不等于"怪硬"。星罗棋布实测混进塔顶的两条是`headhunter_mod:helperchargecontinuepistol`（1000 血、速度 0）与 `headhunter_mod:shadow_grab_hand`（999 血），旧黑名单一条都没挡住——它是带下划线的写法（`helper_`、`_beam`），而这类 mod 把名字连成一串。现在共六道：①血量 > `--max-health`；②`attack_damage <= 0`；③带下划线的旧正则黑名单；④`EFFECT_NAME_TOKENS`——**只看冒号后面那段与类名**、去掉分隔符再比（拿整条 id 比会误杀：命名空间`block_factorys_bosses` 自带 "lock"，`goety:warlock` 这种真法师也跟着挨刀）；⑤血量顶到 999 以上又不会移动（速度 ≤ 0）；⑥**出包之后再按最终产物扫一遍**（`audit_output_shapes`），扫到就不铺叠加层——①~⑤ 挡的是"进池子之前"，而池子会被 `--add-exclude` 与以后的新模组绕过，按产物扫才叫约束。

同一轮还修了顶阶的**倒挂**：`build_challenge` 原先三档各挑各的池子（easy 取本阶、normal/hard 往上一阶取），到最后一阶上面没有更硬的档了，于是 easy 按 ×1.0 挑到 950 血的、hard 为了不被 1024 夹平只能挑 555 血以下的——**玩家选"最难"反而打更软的怪**（`[950.0, 842.4, 842.4]`）。现在三档共用一份池子，池子按 `hp × 1.8 ≤ CEILING` 筛，有效血量变成同一批基础血量的 ×1.0 / ×1.35 / ×1.8 ⇒ `[500.0, 675.0, 900.0]`，既严格上升又没有一只被夹平。
这条是剔掉特效实体之后才暴露的：旧池子里那几只 1000 血的假怪把三档一起顶到天花板，把倒挂遮住了。

## 4h 与「恶意」(l2hostility) 联动（2026-10-12 ㊶）

用户报的冲突：整合包里 `l2hostility-2.5.19` 给怪附加上千级数值，本模组自己的血量阶梯被抹平。
裁定（同日）：**恶意等级跟着层数/档位走并封顶**，这样「第几层」仍然读得出来。

取证是拆它的 class 得到的（`javap -c -constants`，不是猜的）：

| 事实 | 出处 |
| --- | --- |
| 等级住在 `MobTraitCap.lv`，`init(...)` 无条件 `putfield lv` | `MobTraitCap` 字节码 |
| 它初始化怪的那一步是 `MobTraitCap#tick`：`!isInitialized()` 时取 `ChunkDifficulty.at(维度, 坐标)` | 同上的 `tick` 前半 |
| 挂在 `MobSpawnEvent.FinalizeSpawn` 上的 `CapabilityEvents#onEntitySpawn` 只对走 `finalizeSpawn` 的怪生效；我们的怪走 `EntityType#create` + `addFreshEntity`，**不触发** | `CapabilityEvents` 与 `TrialManager.createMobAt` 两边对读 |
| `setLevel(entity, lv)` = `lv = clampLevel(entity, lv)` 再 `TraitManager.scale(...)`；`clampLevel` 只夹上界（全局 `max_mob_level` + 按生物类型），最终生效的是三方最小的那个 | `MobTraitCap` |
| 重复落笔安全：`scale` 加的属性修正用 `MathHelper.getUUIDFromString(name)` 派生的**固定 UUID**，`addAttribute` 先按 UUID 摘旧的再挂新的 ⇒ 不叠层 | `TraitManager.addAttribute` |
| 它自己那条命令是 `/hostility mobs <targets> level set <int>`（`requires(source -> source.hasPermission(2))`），内部就是 `commandSetLevel` = `setLevel` + `syncToClient` | `HostilityCommands` / `LHMobCommands` |
| **它没有 `api` 包** ⇒ 不引它的编译期依赖，全部按类名反射；拿不到就退化成「不联动」并且只在日志里说一次 | jar 目录清单 |

于是 `MaliceLink` 的形状是：生成时**记下**目标等级 → 服务端 tick 收队列 → 等它那侧初始化好
（`isInitialized()`）再落笔（`setLevel` + `syncToClient`，与它自己的命令同一对调用）→ **落一次就忘掉**，
之后玩家手动改那只怪我们不抢。等不到（`malice.reassert_ticks` 用尽、或该生物类型被它排除）就放手，不影响下一只。

三个落笔点对应四种玩法的阶梯序号：守塔/试炼/爬塔用 `session.waveIndex`（爬塔就是层号减一），
闯关用难度档序号（浅/中/深 = 0/1/2）。等级与一条 **请求台账**（`Request(怪, 阶梯序号, 算出的等级, 是否被单只怪覆盖)`，环形留 128 条）算在**所有闸门之前**：台账记的是「我们报了几次、报的是几级」，不是「它改成了几级」，所以没装恶意的机器上也看得见——运行期门因此能拿真开局回读接线（`probeMaliceWiring`），而不是只剩「源码里那三行还在不在」这种形状账。单只怪可写 `malice_level` 覆盖阶梯——字段类型用 `Integer` 而不是 `int`，
`0` 是「明说这一档不带恶意」，`null` 才是「没写、跟着阶梯」。

现场自检：`/tei malice status`（在不在场 / 五项配置 / 阶梯前 8 级 / **生成点请求台账** / 排队数）与
`/tei malice probe [等级]`（就近一只怪：能不能拿到能力、初始化了没、当前几级、写下去读回来是几级）。

## 5 明确还没有的东西（当前边界）

- **多人只做到"不互相损坏"，没做到"互相配合"**：大厅每次 `enterLobby` 都会 `clearLobbyDecor` 再重铺装饰（`ArenaService.buildShrine` 一族），另一个人正好站在装饰位上时会被砌进方块里。拆台/摆放全走 `setBlock`（工程里没有任何 `destroyBlock`），所以不会掉出物品、也不会把别人的东西吞进虚空；但"两个人同时在大厅"这个场景没有专门判据，也没有真机验证（R9 多人那半条一直开着）。
- **恶意联动「写进去读不读得回来」这一半没在无头门上验过**：本工程的 JVM 里没有 `l2hostility`，`probeMaliceLink` 钉得住的是纯决策（该写多少、该不该写、没装那模组时整条路关死、`malice_level` 不被会话副本吃掉），钉不住的是真把它那侧的 `MobTraitCap` 改到位——那一条只能到装了恶意的整合包里跑 `/tei malice probe <等级>`，看「写下去读回来」是不是同一个数（判据自己会说不一致，见 §4h）。**2026-10-12 ㊸ 已在星罗棋布影子实例补验**：同一只僵尸上四档写入回读一致，且它 `Attributes` 里 `hostility_health` 的幅度正好等于 `等级 × healthFactor(0.03)`（5→0.15 / 0→0.0 / 500→15.0 / 30→0.9），全程只有一条修正——"我们写的数它真拿去算血量"成立。它那边类名改了会退化成不联动并在日志里说一次。
- **自动机只挡了交互这一头**：`TrialEvents.playerInitiated` 挡住了 FakePlayer/发射器点我们的三种终端（自测 `probeTerminalContract` 用 `FakePlayerFactory` 真跑过这一条），但 `BlockEvent.EntityPlaceEvent` 那条禁放置也只认 ServerPlayer——非玩家来源仍能在场地维度里放方块。

## 8 环境与构建坑

- **中文路径**（`Documents\开发\...`）：编译打包与 `run*` 实测不受影响，但 Gradle 的 `Test` 任务加载不了测试类
  → 校验一律 `JavaExec`（`checkTrialData` 就是这个模式），**不要引入 `src/test/java` + `Test`**。
- **`gradle.properties` 按 ISO-8859-1 读取**：里面写中文会在生成的 `mods.toml` 里变 mojibake。元数据保持全 ASCII，中文名走 lang 文件。
- **工具进程不要初始化 logger**：`src/tools/java` 的 classpath 上 slf4j 与 log4j 桥接版本不匹配
  （`AbstractMethodError: SLF4JServiceProvider...` / `NoClassDefFoundError: org/slf4j/spi/LoggingEventBuilder`）。
  所以 `TrialDataCheck` 只碰纯模型类，**不引用带 static logger 的类**（例如 `BossAffixLibrary`），槽位名一类的深度校验交给运行期日志。
- **1.20.1 的 brigadier 没有 `CommandDispatcher#getChild/getAllNames`**：要在断言里证明指令可用，
  用 `server.getCommands().performPrefixedCommand(server.createCommandSourceStack(), "tei trial list")` 真执行一遍。
- **产物只用 `build/libs/`**（已 SRG 重混淆）；`build/devlibs/` 是开发版，不要发布。
- **`gradlew` 没有 Unix 可执行位**：Linux CI 需要先 `chmod +x gradlew`；`.github/workflows/build.yml` 还是 MDK 原样（且用 JDK 21 跑 Gradle，工具链仍要求 17），当前没接远端。
- **`run*` 之后若报文件被锁**：`./gradlew --stop` 关掉残留 daemon 子 JVM。
- **验证通道优先级**：`build`（含数据闸门）→ `runGameTestServer -PselfTest`（运行期断言）→ 有玩家时再谈 `runClient`。

## 8b 场地这一轮踩到的坑（都是当场撞出来的）

- **`runGameTestServer` 退 0 不代表自测跑过**：`dimension_type` 少一个必填字段会让服务端在注册表阶段就崩，而 Gradle 仍然 BUILD SUCCESSFUL。

## 8d 房间这一轮踩到的坑（2026-09-26）

- **同一份场地有两套 y 约定就是灾难**：`ArenaService` 的约定是「`origin.y` 这一层就是地板，玩家站 `+1`」，
  我写 `RoomBuilder` 时把地板铺在 `origin.y-1`——于是走廊（按平台的 y）与房间差一格，玩家走进新房要掉一下，
  而且站怪点算在 `origin.y+1` 就成了悬空一格。修法不是改测试，是**把建房统一到平台那条约定**，
  再用「地板必须落在 `origin.y`」这条断言钉住。
- **门洞开错面**：房间沿 +Z 排开、走廊从 `-Z` 侧接过来，门洞却要开在 `dz == d`（远离玩家那一面）＝玩家走到一堵墙前。
  现在是 `dz == -1`。日志/提示里那句「往北进一间」也是错的：`+Z` 在 MC 里是**南**，改成「往里进一间」。
- **force 与 unforce 的盒子不对称 = 永久内存泄漏**：`RoomBuilder` 原先按 `((max(w,d)+4)>>4)+1` 一圈区块去 force，
  拆场却只按平台范围 unforce——多 force 的那几块永远挂在存档里。现在建房只 force **真正会写方块的那些区块**，
  拆场按房间库的最大尺寸算盒子，两边覆盖同一批区块，并有断言（`ServerLevel.getForcedChunks()` 查房内区块）兜住。
- **清场尺寸必须向房间库要，不能写死**：今天的房最宽 19，塞得进按平台半径算的盒子，所以那两条断言是空转的；
  补一个运行期现造的 31×12×21 探针房才咬得住（§3 变异抽查那段）。
- **围栏挡在自家的门上**：平台外圈一行玻璃是防踩空的，但试炼隔间要沿 +Z 往外建房——玩家清完一波得回平台终端继续，
  结果被自己台的围栏堵在台面上。现在 `mode == TRIAL` 时南侧中间 3 格不铺围栏（与走廊同宽），
  **其余三面照旧**（门外是虚空，四面全开门等于挖坑）。这条也是断言（含反例那半边）。
- **房间只开进侧门是刻意的**：一进门就封死、打完走回平台终端继续/结算，所以房与房之间不需要"打通到下一间"的出口；
  真要给房开 +Z 侧的门，就得同时给"下一间还没建"的门口补地板，否则那格是空洞。
- **`/tp` 的 yaw 与直觉相反**：`yaw 0` 是 `+Z`（南），`yaw 180` 是 `-Z`（北）。我按「180 朝 +Z」摆的机位
  全部拍成背对房间的空虚空，白跑三轮才反应过来。
- **拍照机位本身会触发越界判定**：站到 42 格外的空中俯瞰，5 秒宽限一到会话就作废——
  机位必须留在「平台半径圈 ∪ 已建区域」里（`abandon_distance` 默认 48，但竖向距离也算）。
- **玩家死着的时候所有 `key tap` 都打在 `DeathScreen` 上**：表现为「右键没反应、`use()` 连日志都没有」，
  而且 `status.xyz` 看着完全正常。每一步先断言 `screen=="none" && hp>0`，死了先点「重生」。
- **`/api/chat` 是增量游标，屏幕上的聊天栏却是历史**：截图里看到的「已离开试炼范围」可能是上一场留下的，
  别拿它当本轮证据；要判定就当场 `say` + 读增量。
- **拆完场再查方块会假报「仍有方块」**：`/execute if block` 在**未加载区块**里返回 false，

- **`data get block` 只能读方块实体**：拿它查普通方块会得到「目标方块不是方块实体」，

- **`RandomSource` 没有 `create(long, long)`**：只有 `create()` / `create(long)` / `createThreadSafe()` /

## 8e 设计复审这一轮的测量结果（2026-09-26，全部当场跑出来的）

- **离线门那个工具 JVM 连 `BlockPos` 都不能碰**：`checkTrialData` 是纯 JavaExec 进程，没有 log4j 实现，
  而 `BlockPos` 的类初始化会去 `LogUtils.getLogger()`。2026-09-28 ㉕ 我就踩了：隔断校验里用了
  `spawnPointsAt(BlockPos.ZERO)`，编译过、`build` 直接炸在 `NoClassDefFoundError: org/slf4j/spi/LoggingEventBuilder`。
  ⇒ 数据校验只能用纯类型（int/String/ResourceLocation——后者不拉日志所以没事），要 MC 坐标就把
  "怎么排"算成 int 再交给 `BlockPos` 偏移。同一族坑第 N 次命中，见 [[forge-1201-headless-assert-channel]]。
- **无头自测 JVM 里实体进不了可查询状态**：`ServerStartedEvent` 之后 `runGameTestServer` 一条 tick 都不跑
  （日志里紧跟着就是 `Stopping server`），而 `addFreshEntity` 的怪只进了实体管理器的任务队列。
  实测在探针里手动 `arenaLevel.tick(() -> true)` 推 **20 次**，`getEntity(uuid)` 与 `getEntitiesOfClass(box)`
  仍然全是空。⇒ 「扫怪真把怪清掉了」这条**不可能**在这道门里变绿，只能真机验（#20）；
  门里能验的是盒子覆盖面、记账、方块数。曾经写过一条 `sweepCellMobs(...) >= 0` 的断言——那是永真式，
  已经删掉；同理第一版"换段回收"断言只查记账，也是空的（`put` 覆盖本来就会让旧值消失），改成查方块数。
- **隔间扩展性的实际数字**（默认配置：半径 10、间隔 160、清场 `half=12`、`topY=11`）：
  平台约 520 个非空气方块；拆场扫描 reach=0 是 25×13×33 ≈ **10.7k 个位置**（其中约 2.6k 次真 `setBlock`），
  reach=44（现有房间表串到最深）是 25×13×77 ≈ **25k 个位置**；
  每间常驻 **6～12 个强制加载区块柱**（`FORCED_TICKET_LEVEL = ENTITY_TICKING`，会 tick 也会自动存档）。
  坐标没有溢出风险：`cell * spacing` 最大约 12.3M，远小于 `int` 与 `SectionPos` 的 ±33.5M。
  ⇒ 结论：现在这个量级（1 人 1 间）不卡；真正会疼的是"多人同时离场"把几次 2.6k 次 `setBlock` 挤进同一 tick。
  **没改**（不过度工程），要改就两条：`UPDATE_ALL` 降级（场地方块没有 `neighborChanged`，无方块实体）
  或把 `releaseCellAt` 按 tick 预算分摊。
- **审出来但没动的一条设计问题**（要拍板，见 §9 第 9 条）：副本杀怪奖励走的是"轮询发现 UUID 不在场就算死"
  （`pruneDeadMobs`），不认凶手。摔进虚空、溺亡、怪互殴都会照发奖励，波次也会因此提前放行。
